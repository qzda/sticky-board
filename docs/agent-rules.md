# 开发与 Agent 约束

本文档约束所有后续参与 Sticky Board 项目的自动化 agent、AI 编码助手和人工协作者。

## 最高优先级规则

未经用户明确允许，任何 agent 不准执行：

- `git commit`
- `git push`
- 创建 tag
- 发布 release
- 修改远程仓库配置
- 强制回滚或重置用户改动

即使代码已经通过构建或测试，也必须等待用户明确授权后才能 commit 或 push。

## 提交规则

只有用户明确要求提交代码时，agent 才能执行 `git commit`。

提交信息必须符合 [Angular Team Commit Specification](https://github.com/angular/angular.js/blob/master/DEVELOPERS.md#-git-commit-guidelines)。

提交信息格式：

```text
<type>(<scope>): <subject>
```

要求：

- `scope` 可选。
- `type` 使用 Angular 规范中的类型，例如 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`。
- `subject` 使用简短祈使句，不以大写开头，不以句号结尾，但不能遗漏本次提交的主要用户可见改动。
- `subject` 与 `body` 尽量使用中文描述；技术名词、变量名、函数名、类型名、API 名等固定标识不用强制翻译。
- 任意一行不超过 100 个字符。
- 需要正文或 footer 时，header、body、footer 之间用空行分隔。
- 当改动涉及多个功能点、多个架构边界或大量文件时，必须写 body。
- 当改动很小，例如只更新某一项规则的几句话、修正文案或窄范围单点修改时，可以只写 header，不需要 body。
- body 可以使用 Markdown 语法，优先使用 `- ` 列表逐条说明关键改动。
- body 应覆盖主要行为变化、依赖变化、文档同步和重要验证结果；不要只重复 header。
- Breaking Change 必须在 footer 中用 `BREAKING CHANGE:` 标记。
- 提交信息不要添加 `Co-Authored-By` 署名，也不要署名任何 AI 或自动化工具。

示例：

```text
feat(import): 支持从 zip 导入便签图片

- 解析 sticky-board-config.json 恢复便签布局。
- 将相对图片路径转换为 sticky-image:// 内部链接。
- 验证导入后图片与 Markdown 预览一致。
```

无论用户是否要求 commit，agent 永远不准执行 `git push`。push 必须由用户自己完成。

## 当前阶段限制

Sticky Board 是本地优先的浏览器便签板。除非用户明确要求，否则不要：

- 添加第三方依赖。
- 引入后端服务、账号系统、云同步、遥测或分析 SDK。
- 上传便签内容、粘贴图片、导入文件或任何本地数据到外部服务。
- 大规模重构无关模块。
- 切换包管理器、删除 lockfile 或重写构建配置。

## 文件与职责边界

实现阶段必须遵守：

- 入口与核心交互集中在 `src/main.ts`，样式集中在 `src/style.scss`。
- `docs/ARCHITECTURE.md` 是当前行为的架构说明，重大行为变更必须同步更新。
- Markdown 渲染规则应集中在 `markdown-it` 初始化和 renderer override 附近。
- IndexedDB 读写应通过现有 `openAppDb`、`readPersistedValue`、`writePersistedValue` 等存储入口完成。
- 便签数据必须保持 `Sticky` / `Stickys` 模型语义，不随意扩展持久化字段。
- 图片内部引用必须使用 `sticky-image://<imageKey>`，不要引入额外内部 URI scheme。
- ZIP 导入导出必须保持 `.md + images + sticky-board-config.json` 的可读目录结构。
- 时间轴布局和自由拖拽布局必须保持互斥，不让同一张卡片同时处于两种布局状态。

## 隐私与本地优先

Sticky Board 默认纯本地。便签文本和粘贴图片可能包含用户隐私或敏感资料。

任何 agent 编写或修改代码时，都必须保持：

- 便签和图片只在浏览器本地处理，不上传、不同步到远程服务。
- 不引入默认联网、遥测、崩溃上传或分析 SDK。
- 不把便签内容、图片 Blob、导入文件内容写入外部日志或第三方存储。
- 任何未来可能联网的能力都必须经过用户明确确认，并写入 `/docs` 下对应文档。

## 文档优先

当新增或修改以下能力时，应同步更新 `/docs` 下相关文档：

- 便签数据模型或持久化格式。
- IndexedDB key、store、版本或迁移策略。
- Markdown 渲染规则、图片引用格式或安全策略。
- 粘贴图片限制、清理策略或对象 URL 生命周期。
- ZIP 导入导出文件结构、路径映射或兼容规则。
- 交互行为，例如拖拽、缩放、创建、编辑、预览、时间轴布局。
- 主题、视觉层级或 PWA 配置。

文档和实现发生冲突时，必须在提交前统一；不能让文档长期描述不存在或相反的行为。

## 依赖约束

新增第三方依赖前必须说明：

- 解决什么问题。
- 为什么现有浏览器 API 或已安装依赖不足。
- 对包体积、启动性能、构建速度和维护成本的影响。
- 是否会读取、上传或处理便签、图片、导入文件或本地存储数据。

未经用户允许，不得添加会上传本地数据、采集用户行为、接入远程服务或改变隐私边界的依赖。

## 测试与验证

默认验证优先运行：

```bash
pnpm build
```

如果当前任务或用户明确使用其他包管理器，则使用与当前工作流一致的等价命令。

涉及交互或浏览器行为时，应优先验证：

- 新建便签、拖拽、缩放后位置和尺寸能持久化。
- 右键编辑、点击空白处预览、删除确认行为正常。
- Markdown 链接、图片、代码块、引用块、表格等常见元素渲染正常。
- 粘贴图片后能预览，刷新后仍能显示。
- 删除或移除图片引用后，未引用图片会被清理。
- ZIP 导出后 Markdown 文件能使用相对路径查看图片。
- ZIP 导入后便签、图片和布局能恢复。
- Sunny 主题、深色模式、减少动态效果和时间轴布局没有明显视觉回归。

## 协作礼仪

- 不擅自重构无关文件。
- 不覆盖用户未提交改动。
- 不因为构建失败就回滚用户改动。
- 遇到需求不明确时，优先做小范围、可解释、可回退的改动。
- 输出结论时说明改了哪些文件、没有改哪些文件、是否运行了验证。
